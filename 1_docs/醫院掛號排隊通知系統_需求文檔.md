# 叮咚到號 — 醫院看診進度即時通知系統 需求與技術規劃文檔

> 版本：v0.1 | 日期：2026-03-28 | 狀態：需求規劃階段

---

## 一、專案概述

### 1.1 專案目標

開發一套通用平台，自動抓取台灣各大醫院的門診即時看診進度資料，透過 LINE 官方帳號推播通知用戶，讓用戶不需反覆查看醫院網站，即可在快輪到自己看診時收到提醒。

### 1.2 核心價值

- 減少病患在醫院的等候時間，提升就醫體驗
- 支援多家醫院、可擴展的通用架構
- 透過 LINE（台灣最普及的通訊軟體）觸及最多用戶

### 1.3 目標用戶

已在醫院完成掛號、持有掛號序號的門診病患。用戶希望在看診號碼接近時收到通知，以便合理安排等候時間。

## 三、資料來源調研

### 3.1 MVP 首發醫院：萬芳醫院（已完成頁面分析）

| 項目 | 內容 |
|------|------|
| 醫院名稱 | 臺北市立萬芳醫院 |
| 看診進度網址 | `https://wwww.wanfang.gov.tw/reg/register_visits_cload3.aspx` |
| 網頁技術 | ASP.NET WebForms + UpdatePanel |
| 資料取得方式 | **HTTP GET 直接取得完整 HTML，解析 `.card-panel` 元素** |
| 自動更新 | 頁面每 60 秒 meta refresh 自動刷新 |
| 科別分類 | `#01` 內科系、`#02` 外科系、`#03` 婦兒科、`#04` 其他科別、`#05` 特別門診 |
| 所有科別資料 | 一次性全部載入，hash 僅做頁面內錨點跳轉 |

#### 頁面 HTML 結構（每個診間一張 `.card-panel`）

每張卡片的 `innerText` 結構如下：

```
2026/03/28  上午診        ← 日期 + 診別（早診/午診/夜診）
精神科                    ← 科別名稱
許元彰                    ← 醫師姓名
282診                     ← 診間號碼
45    46                  ← 目前號碼 \t 下一號碼
目前號碼  下一號碼         ← 標題列
(過號)                    ← 可選，出現在目前號碼或下一號碼下方
```

#### 解析後的標準化資料範例

```json
{
  "hospital_id": "wanfang",
  "hospital_name": "萬芳醫院",
  "date": "2026/03/28",
  "session": "上午診",
  "department": "精神科",
  "doctor_name": "許元彰",
  "clinic_room": "282診",
  "current_number": 45,
  "next_number": 46,
  "is_skipped": false,
  "updated_at": "2026-03-28T15:27:40+08:00"
}
```

#### 爬蟲策略

1. 直接 GET 請求 `register_visits_cload3.aspx` 即可取得所有看診中的診間資料
2. 使用 BeautifulSoup 解析 HTML，定位所有 `.card-panel` 元素
3. 不需要處理 ASP.NET ViewState/PostBack（純 GET 就能拿到資料）
4. 建議爬蟲間隔 60 秒（與頁面自身刷新頻率一致）

### 3.4 法律與合規注意事項

- 爬取公開的看診進度資訊（號碼、科別）不涉及個人隱私資料
- 需遵守各醫院網站的 robots.txt 規範
- 控制爬蟲頻率（60 秒/次），避免對醫院伺服器造成負擔
- 建議在服務條款中說明資料來源與免責聲明
- 如有醫院要求停止抓取，應立即配合

### 4.2 技術棧選型

#### 後端框架

| 選項 | 推薦 | 理由 |
|------|------|------|
| **Python + FastAPI** | ✅ 推薦 | 爬蟲生態成熟（requests, BeautifulSoup, Playwright）、async 支援佳、開發速度快 |
| Node.js + NestJS | 備選 | 適合即時應用，但爬蟲生態不如 Python |

#### 資料庫

| 組件 | 選擇 | 理由 |
|------|------|------|
| 主資料庫 | **MySQL 8.0+** | 由 aaPanel 管理（外部），熟悉度高、維運簡單、JSON 欄位支援足夠 |
| 快取層 | **Redis** | 存放即時看診進度快取、任務佇列、rate limiting |

#### 爬蟲引擎

| 工具 | 用途 |
|------|------|
| **httpx** (async) | API 直接呼叫（優先使用） |
| **BeautifulSoup4** | HTML DOM 解析 |
| **Playwright** | 需要 JavaScript 渲染的動態頁面（備用） |

#### 任務排程與佇列

| 組件 | 選擇 | 理由 |
|------|------|------|
| 任務佇列 | **Celery + Redis** | 成熟穩定、支援定時任務與 retry |
| 定時排程 | **Celery Beat** | 內建排程器，可動態調整頻率 |

#### LINE 整合

| 組件 | 選擇 |
|------|------|
| SDK | **line-bot-sdk-python** |
| 帳號類型 | LINE Official Account（Messaging API） |
| 訊息類型 | Push Message（主動推播）、Reply Message（回覆查詢） |
| Rich Menu | 提供圖形化選單，方便操作 |

#### 部署環境

| 組件 | 選擇 | 理由 |
|------|------|------|
| 伺服器管理 | **aaPanel** | 你熟悉的面板，方便管理 Nginx、SSL、MySQL |
| 容器化 | **Docker + Docker Compose** | 應用隔離、一鍵部署、易於更新 |
| 反向代理 | **Nginx**（aaPanel 內建） | 處理 HTTPS、LINE Webhook 入口 |
| SSL | **Let's Encrypt**（aaPanel 自動續簽） | LINE Webhook 要求 HTTPS |

### 4.3 部署架構（aaPanel + Docker）

```
┌─ VPS 主機 ──────────────────────────────────┐
│                                              │
│  ┌─ aaPanel 管理 ────────────────────────┐   │
│  │  Nginx (反向代理 + SSL)               │   │
│  │  ├─ /webhook  → app:8000              │   │
│  │  ├─ /admin    → app:8000              │   │
│  │  MySQL 8.0 (aaPanel 安裝 & 管理)      │   │
│  │  ├─ port 3306 (僅限 localhost)        │   │
│  │  └─ phpMyAdmin 可視化管理             │   │
│  └───────────────────────────────────────┘   │
│                                              │
│  ┌─ Docker Compose ──────────────────────┐   │
│  │  ┌──────────┐  ┌──────────┐           │   │
│  │  │  app     │  │  worker  │           │   │
│  │  │ (FastAPI)│  │ (Celery) │           │   │
│  │  └──────────┘  └──────────┘           │   │
│  │  ┌──────────┐  ┌──────────┐           │   │
│  │  │  beat    │  │  redis   │           │   │
│  │  │ (排程器) │  │ (快取)   │           │   │
│  │  └──────────┘  └──────────┘           │   │
│  └───────────────────────────────────────┘   │
```

MySQL 由 aaPanel 直接安裝管理，不放在 Docker 內。Docker 容器透過 `network_mode: host` 或 `extra_hosts: ["host.docker.internal:host-gateway"]` 連線到主機上的 MySQL（127.0.0.1:3306）。這樣可以用 aaPanel 的 phpMyAdmin 直接管理資料庫，備份還原也方便。

## 五、核心流程

### 5.1 用戶查詢流程（簡化版 — 無需掛號號碼即可使用）

用戶加入 LINE 官方帳號後，直接輸入查詢條件即可獲得即時看診進度。

**查詢方式：用戶發送文字訊息**

```
用戶輸入格式（彈性匹配，支援以下幾種）：
  「萬芳 精神科」           → 回傳精神科所有診間進度
  「萬芳 許元彰」           → 回傳許元彰醫師的診間進度
  「萬芳 282診」            → 回傳 282 診的看診進度
  「萬芳 精神科 許元彰」    → 精確匹配
```

**Bot 回覆格式：**

```
03/28 15:24 萬芳醫院-精神科 許元彰 282診 目前45號 46下一號
03/28 15:24 萬芳醫院-骨科部 陳建樺 106診 目前58號(過號) 69下一號
```

### 5.2 用戶訂閱追蹤流程（進階 — 主動推播提醒）

```
用戶發送「追蹤 萬芳 精神科 許元彰 我是60號」
    │
    ▼
系統建立追蹤任務，存入資料庫
    │
    ▼
回覆確認：「已開始追蹤 萬芳醫院 精神科 許元彰 282診，您是第 60 號，
           目前看到第 45 號，還有約 15 位。快到時會通知您！」
    │
    ▼
系統每 60 秒抓取進度，當 current_number >= 60 - threshold 時推播：
    │
    ▼
「您的看診號碼快到了！
 萬芳醫院-精神科 許元彰 282診
 目前看到第 55 號，您是第 60 號
 預計還有約 5 位」
```

### 5.3 即時資料抓取流程

```
Celery Beat 每 60 秒觸發爬蟲任務
    │
    ▼
GET https://wwww.wanfang.gov.tw/reg/register_visits_cload3.aspx
    │
    ▼
BeautifulSoup 解析所有 .card-panel 元素
    │
    ▼
標準化為統一格式，更新 Redis 快取
    │
    ▼
比對所有活躍追蹤任務 → 觸發推播
```

### 5.3 爬蟲 Adapter 架構

每家醫院實作一個 Adapter，遵循統一介面：

```python
# 概念示意，非實際代碼
class BaseHospitalAdapter(ABC):
    hospital_id: str
    hospital_name: str

    @abstractmethod
    async def fetch_progress(self, department: str, clinic_room: str) -> ClinicProgress:
        """抓取指定科別/診間的看診進度"""
        pass

    @abstractmethod
    async def list_departments(self) -> list[Department]:
        """取得該醫院所有科別列表"""
        pass
```

## 八、非功能性需求

### 8.1 效能

- 爬蟲輪詢頻率：每 1-3 分鐘一次（可依醫院/時段動態調整）
- LINE 推播延遲：從偵測到號碼接近到送出通知 < 30 秒
- 系統需支援同時追蹤 1,000+ 筆任務

### 8.2 可靠性

- 爬蟲失敗自動 retry（最多 3 次，指數退避）
- 醫院網站無法連線時，暫停該醫院爬蟲並通知管理員
- 推播失敗重試機制

### 8.3 可擴展性

- 新增醫院只需撰寫一個 Adapter 模組，不需修改核心邏輯
- 資料庫 schema 支援未來新增欄位（如候診人數、預估等候時間）

### 8.4 安全性

- LINE Webhook 驗證簽章（X-Line-Signature）
- 管理後台需登入驗證
- 不儲存任何病患醫療隱私資料（僅掛號號碼）

## 十、風險評估

| 風險 | 影響 | 緩解措施 |
|------|------|----------|
| 醫院網站改版 | 爬蟲失效 | 異常告警 + Adapter 快速更新機制 |
| 被醫院封鎖 IP | 無法抓取 | 控制頻率、使用合理 User-Agent、必要時輪換 IP |
| LINE 訊息費用超支 | 營運成本增加 | 優化推播策略、善用 Reply Message |
| 資料不準確 | 用戶體驗差 | 訊息中標註「僅供參考」+ 顯示更新時間 |
| 法律合規風險 | 被要求停止 | 僅抓取公開資料、配合醫院要求、準備替代方案 |
